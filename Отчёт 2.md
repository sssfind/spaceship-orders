# Отчёт 2

## Запуск в Minikube

Приложение Spaceship Orders развёрнуто в кластере Minikube. В кластер входят четыре процесса: Order Service вместе UI, IAM Service и два экземпляра PostgreSQL  - отдельная бд для заказов и пользователей и сессий 

Образы `order:latest` и `iam:latest` собираются из `deploy/docker/order/Dockerfile` и `deploy/docker/iam/Dockerfile`. Манифесты лежат в `deploy/k8s/` и применяются в namespace `spaceship`

---

## Какие абстракции Kubernetes использованы


| Абстракция            | Где используется                      | Зачем                                                                                                                |
| --------------------- | ------------------------------------- | -------------------------------------------------------------------------------------------------------------------- |
| Namespace             | `spaceship`                           | Отделяет объекты приложения от остальных объектов кластера                                                           |
| Pod                   | создаётся каждым Deployment           | Запускает контейнер приложения или PostgreSQL                                                                        |
| Deployment            | `order`, `iam`, `orders-db`, `iam-db` | Держит нужное число реплик и перезапускает упавший контейнер. `kubectl scale` меняет число реплик Order и IAM        |
| Service               | те же четыре имени                    | Даёт стабильное DNS-имя и порт внутри кластера. Для `order` тип `NodePort` (`30081`), остальные - `ClusterIP`        |
| ConfigMap             | `order`, `iam`                        | Несекретная конфигурация: адрес и порт HTTP, хост PostgreSQL, `IAM_HTTP_BASE_URL`, каталог миграций, параметры логов |
| Secret                | `order`, `iam`, `orders-db`, `iam-db` | Учётные данные PostgreSQL (`POSTGRES_USER`, `POSTGRES_PASSWORD`)                                                     |
| PersistentVolumeClaim | `orders-db`, `iam-db`                 | Хранит данные PostgreSQL на диске и сохраняет их при перезапуске пода                                                |


Пробы готовности и живости читают `GET /health` у Order и IAM и вызывают `pg_isready` у PostgreSQL. Пока проба не проходит, Service не отправляет трафик в под. Init-контейнер `busybox` перед стартом Order и IAM ждёт, пока поднимется порт базы, а Order дополнительно ждёт порт IAM.

У баз стоит `replicas: 1` и стратегия `Recreate`. Том заявлен как `ReadWriteOnce`, его нельзя смонтировать в несколько подов одновременно. Order и IAM состояния на диске пода не хранят, поэтому их можно масштабировать: на демонстрации Order до трёх реплик, IAM до двух. У образов приложений `imagePullPolicy: Never` - кластер берёт локально собранные образы и не обращается в registry

## Как сервисы взаимодействуют

Браузер открывает только Order. UI и HTTP API раздаёт один и тот же процесс. Запросы аутентификации UI отправляет на Order по путям `/api/v1/auth/*`, а Order проксирует их в IAM.

Связь идёт по DNS-именам Service, а не по IP подов:

```text
Браузер
   │  NodePort 30081 / minikube service order
   ▼
Service order:8081 ── поды Deployment order
   │
   ├── PostgreSQL  orders-db:5432   база orders
   └── HTTP        iam:8082         whoami и прокси /api/v1/auth/*
                         │
                         └── PostgreSQL  iam-db:5432   база iam
```


| Кто     | Куда                     | Как задано                                             |
| ------- | ------------------------ | ------------------------------------------------------ |
| Браузер | Order                    | Service `order`, порт `8081`, снаружи NodePort `30081` |
| Order   | PostgreSQL заказов       | `POSTGRES_HOST=orders-db`, порт `5432`, база `orders`  |
| Order   | IAM                      | `IAM_HTTP_BASE_URL=http://iam:8082`                    |
| IAM     | PostgreSQL пользователей | `POSTGRES_HOST=iam-db`, порт `5432`, база `iam`        |


Order и IAM при старте сами применяют миграции goose (`MIGRATION_DIRECTORY=migrations`). Сессии и заказы лежат в PostgreSQL, поэтому несколько реплик одного Deployment работают с одной базой через общий Service. После `kubectl scale` URL интерфейса не меняется: Service распределяет запросы по готовым подам
