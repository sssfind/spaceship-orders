# Отчёт

## 1. Доменная область приложения

Приложение **Spaceship Orders** предназначено для управления заказами на сборку космических кораблей.

Пользователь (клиент) формирует заказ из набора комплектующих (деталей), система рассчитывает стоимость, фиксирует заказ в базе данных, позволяет оплатить или отменить заказ, просмотреть список заказов и удалить заказ. Веб-интерфейс и HTTP API предоставляют полный цикл CRUD-операций над сущностью «заказ».

Домен упрощён относительно реальной производственной системы: каталог деталей и платёжный шлюз не выделены в отдельные сервисы; стоимость заказа вычисляется на стороне Order Service по числу позиций.

## 2. Стек реализации

| Слой | Технология |
|:-----|:-----------|
| Язык бэкенда | Go 1.26 |
| HTTP API | REST (HTTP/1.1), OpenAPI 3 + codegen (ogen) |
| Фронтенд | HTML, CSS, JavaScript (статика, раздаётся Order Service) |
| СУБД | PostgreSQL 17 |
| Доступ к БД | pgx/v5 |
| Миграции | goose |
| Конфигурация | переменные окружения (+ `.env` для локальной разработки) |
| Логирование | Zap → stdout (опционально OTLP) |
| Метрики | Prometheus (`/metrics`) |
| Трейсинг | OpenTelemetry (опционально) |
| Контейнеризация | Docker, Docker Compose |
| Автоматизация | Taskfile |
| Архитектура кода | Clean Architecture (api → service → repository) |

Взаимодействие клиента с бэкендом — **HTTP/REST**, без gRPC на внешнем контуре.

## 3. Основные сущности доменной области

### Order (заказ)

Центральная сущность системы. Хранится в таблице `orders`.

| Поле | Тип | Описание |
|:-----|:----|:---------|
| `order_uuid` | UUID | Идентификатор заказа (PK) |
| `user_uuid` | UUID | Идентификатор пользователя |
| `part_uuids` | UUID[] | Список UUID деталей в заказе |
| `total_price` | float | Итоговая стоимость |
| `status` | string | Статус жизненного цикла заказа |
| `transaction_uuid` | UUID? | UUID платёжной транзакции (после оплаты) |
| `payment_method` | string? | Способ оплаты (после оплаты) |

**Статусы заказа:** `PENDING_PAYMENT`, `PAID`, `CANCELLED`, `ASSEMBLED`, `COMPLETED`.

**Способы оплаты:** `CARD`, `SBP`, `CREDIT_CARD`, `INVESTOR_MONEY` (также `UNKNOWN`).

### CRUD-операции над Order

| Операция | HTTP |
|:---------|:-----|
| Create | `POST /api/v1/orders` |
| Read (список) | `GET /api/v1/orders` |
| Read (один) | `GET /api/v1/orders/{order_uuid}` |
| Update (оплата) | `POST /api/v1/orders/{order_uuid}/pay` |
| Update (отмена) | `POST /api/v1/orders/{order_uuid}/cancel` |
| Delete | `DELETE /api/v1/orders/{order_uuid}` |

## 4. Соответствие методологии 12-Factor App

### I. Codebase (кодовая база)

**Соответствует.**

Один репозиторий Git содержит весь исходный код приложения (Order Service, frontend, shared/platform, deploy). Один кодбейз разворачивается в разных окружениях (локально / Docker Compose) одной и той же сборкой. Монорепозиторий с Go Workspaces не нарушает фактор: это один кодбейз, а не несколько несвязанных приложений.

### II. Dependencies (зависимости)

**Соответствует.**

Зависимости Go явно объявлены в `go.mod` / `go.sum` модулей `order`, `shared`, `platform`. Инструменты сборки и качества фиксируются через Taskfile (версии ogen, golangci-lint, goose и т.д.). Для OpenAPI-бандлинга используется `package-lock.json` (Redocly). Изоляция зависимостей обеспечивается модульной системой Go и контейнерной сборкой (multi-stage Dockerfile).

### III. Config (конфигурация)

**Соответствует.**

Конфигурация читается из переменных окружения (`HTTP_*`, `POSTGRES_*`, `LOGGER_*`, `FRONTEND_DIR` и др.) в пакете `order/internal/config`. Секреты и параметры окружения не зашиты в код. Для локальной разработки `.env` подгружается через godotenv, но уже установленные переменные окружения имеют приоритет — это совместимо с 12-factor (config in the environment). Шаблоны: `deploy/env/.env.template`, генерация: `task env:generate`.

### IV. Backing services (подключаемые ресурсы)

**Соответствует.**

PostgreSQL трактуется как подключаемый ресурс: адрес, порт, учётные данные задаются через env (`POSTGRES_HOST`, `POSTGRES_PORT`, …). В Docker Compose хост БД — имя сервиса `orders_db`; с хоста — `localhost`. Смена backing service сводится к смене конфигурации, без изменения кода. Файловое хранилище состояния приложения не используется.

### V. Build, release, run (сборка, релиз, запуск)

**Соответствует (с оговоркой).**

- **Build:** multi-stage Dockerfile собирает бинарник Go и копирует миграции + frontend в образ `order:latest`.
- **Release:** образ + набор переменных окружения (`.env` / Compose) образуют релиз для запуска.
- **Run:** процесс HTTP-сервера в контейнере (`CMD ["./server"]`) или локально (`task run`).

Оговорка: миграции также могут выполняться при старте приложения (удобство dev). Для соответствия фактору XII / чистоты стадий есть отдельная one-off команда `task migrate`. Явный release-ID (semver-тег образа) в пайплайне не обязателен для учебного стенда, но может быть добавлен через теги Docker.

### VI. Processes (процессы)

**Соответствует.**

Order Service — stateless HTTP-процесс. Состояние заказов хранится в PostgreSQL. Sticky-сессии и локальное дисковое состояние приложения не используются. Статический UI — файлы, раздаваемые процессом, без серверной сессии.

### VII. Port binding (привязка к порту)

**Соответствует.**

Приложение само экспортирует HTTP-сервис через `ListenAndServe` на адрес из `HTTP_HOST`/`HTTP_PORT` (по умолчанию в compose — `8081`). Не требуется отдельный контейнер веб-сервера для API; UI раздаётся тем же процессом. Compose пробрасывает порт наружу: `${HTTP_PORT}:${HTTP_PORT}`.

### VIII. Concurrency (параллелизм / масштабирование)

**Соответствует.**

Горизонтальное масштабирование достигается запуском нескольких экземпляров Order Service за балансировщиком (процессы одного типа `web`). Процесс stateless, общая БД — PostgreSQL. В локальном Compose для простоты один реплика; модель процессов допускает scale-out без изменения кода. Отдельный worker-процесс не требуется: вся работа выполняется в HTTP-обработчиках.

### IX. Disposability (утилизируемость)

**Соответствует.**

Быстрый старт: лёгкий статический бинарник на Alpine. Graceful shutdown по SIGINT/SIGTERM через `platform/pkg/closer`: остановка HTTP-сервера (`Shutdown`), закрытие пула БД, логгера и трейсера. Процесс можно безопасно останавливать и перезапускать (например, `docker compose up --build`).

### X. Dev/prod parity (паритет окружений)

**Соответствует.**

Локально и в «стенде» используется один и тот же Docker-образ Order Service и PostgreSQL из Compose. Миграции goose одинаковы. Различия (host `orders_db` vs `localhost`, порты) вынесены в env — это ожидаемый способ сохранить паритет при разных точках подключения. Интеграционные тесты используют Docker/Testcontainers, приближая тестовое окружение к runtime.

### XI. Logs (логи)

**Соответствует.**

Логи пишутся как поток событий в **stdout** (Zap). Приложение не управляет ротацией и хранением логов — этим занимается окружение (Docker / коллектор). При необходимости включается дополнительный вывод в OTLP (`LOG_OUTPUTS`), без записи логов в файлы внутри контейнера приложения.

### XII. Admin processes (административные процессы)

**Соответствует.**

Административные задачи выполняются как one-off процессы в том же окружении:

- `task migrate` — применение goose-миграций к PostgreSQL с хоста;
- `task migrate:status` / `task migrate:down` — статус и откат.

Миграции используют тот же каталог SQL (`order/migrations`) и те же параметры БД из `.env`, что и приложение. Это отделяет admin-задачи от долгоживущего web-процесса.
