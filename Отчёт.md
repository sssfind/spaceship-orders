# Отчёт

## Доменная область приложения

Приложение Spaceship Orders предназначено для управления заказами на сборку космических кораблей.

Пользователь регистрируется и входит в систему (IAM), выбирает комплектующие из каталога деталей, система рассчитывает стоимость по ценам и наличию на складе, фиксирует заказ с позициями в PostgreSQL, позволяет оплатить или отменить заказ, просмотреть список заказов и платежей, удалить заказ. Веб-интерфейс и HTTP API предоставляют CRUD над заказами и деталями, а также учёт платежей.

Домен упрощён относительно реальной производственной системы: каталог деталей и платежи пока живут в Order Service (готовы к выделению в Inventory / Payment в следующих ДЗ).

## Стек реализации


| Слой             | Технология                                               |
| ---------------- | -------------------------------------------------------- |
| Язык бэкенда     | Go 1.26                                                  |
| HTTP API         | REST (HTTP/1.1), OpenAPI 3 + codegen (ogen)              |
| Фронтенд         | HTML, CSS, JavaScript (статика, раздаётся Order Service) |
| СУБД             | PostgreSQL 17                                            |
| Доступ к БД      | pgx/v5                                                   |
| Миграции         | goose                                                    |
| Auth             | IAM Service (register / login / session)                 |
| Конфигурация     | переменные окружения (+ `.env` для локальной разработки) |
| Логирование      | Zap → stdout (опционально OTLP)                          |
| Метрики          | Prometheus (`/metrics`)                                  |
| Трейсинг         | OpenTelemetry (опционально)                              |
| Контейнеризация  | Docker, Docker Compose                                   |
| Автоматизация    | Taskfile                                                 |
| Архитектура кода | Clean Architecture (api → service → repository)          |


Взаимодействие клиента с бэкендом — HTTP/REST. Auth UI ходит на Order (`/api/v1/auth/*`), который проксирует запросы в IAM.

## Основные сущности доменной области

### 1. User (пользователь) — IAM

| Поле            | Тип    | Описание              |
| --------------- | ------ | --------------------- |
| `user_uuid`     | UUID   | Идентификатор (PK)    |
| `login`         | string | Уникальный логин      |
| `password_hash` | string | Хэш пароля            |
| `created_at`    | time   | Время регистрации     |

Операции: регистрация (`POST /api/v1/auth/register`), чтение профиля (`GET /api/v1/auth/whoami`).

### 2. Session (сессия) — IAM

| Поле           | Тип  | Описание                         |
| -------------- | ---- | -------------------------------- |
| `session_uuid` | UUID | Идентификатор сессии (PK)        |
| `user_uuid`    | UUID | Владелец сессии (FK → users)     |
| `expires_at`   | time | Срок действия                    |
| `created_at`   | time | Время создания                   |

Операции: создание при login, удаление при logout, проверка whoami.

### 3. Part (деталь каталога) — Order

| Поле        | Тип    | Описание              |
| ----------- | ------ | --------------------- |
| `part_uuid` | UUID   | Идентификатор (PK)    |
| `name`      | string | Название              |
| `price`     | float  | Цена за единицу       |
| `category`  | string | Категория             |
| `in_stock`  | int    | Остаток на складе     |

**CRUD:**

| Операция | HTTP |
| -------- | ---- |
| Create   | `POST /api/v1/parts` |
| Read (список) | `GET /api/v1/parts` |
| Read (один) | `GET /api/v1/parts/{part_uuid}` |
| Update   | `PUT /api/v1/parts/{part_uuid}` |
| Delete   | `DELETE /api/v1/parts/{part_uuid}` |

### 4. Order (заказ) — Order

| Поле               | Тип     | Описание                                 |
| ------------------ | ------- | ---------------------------------------- |
| `order_uuid`       | UUID    | Идентификатор заказа (PK)                |
| `user_uuid`        | UUID    | Идентификатор пользователя               |
| `part_uuids`       | UUID[]  | Денормализованный список UUID деталей    |
| `total_price`      | float   | Итоговая стоимость                       |
| `status`           | string  | Статус жизненного цикла заказа           |
| `transaction_uuid` | UUID?   | UUID платежа (после оплаты)              |
| `payment_method`   | string? | Способ оплаты (после оплаты)             |

**Статусы:** `PENDING_PAYMENT`, `PAID`, `CANCELLED`, `ASSEMBLED`, `COMPLETED`.

**CRUD:**

| Операция        | HTTP                                      |
| --------------- | ----------------------------------------- |
| Create          | `POST /api/v1/orders`                     |
| Read (список)   | `GET /api/v1/orders`                      |
| Read (один)     | `GET /api/v1/orders/{order_uuid}`         |
| Update (оплата) | `POST /api/v1/orders/{order_uuid}/pay`    |
| Update (отмена) | `POST /api/v1/orders/{order_uuid}/cancel` |
| Delete          | `DELETE /api/v1/orders/{order_uuid}`      |

### 5. OrderItem (позиция заказа) — Order

| Поле         | Тип   | Описание                    |
| ------------ | ----- | --------------------------- |
| `order_uuid` | UUID  | FK → orders                 |
| `part_uuid`  | UUID  | FK → parts                  |
| `quantity`   | int   | Количество                  |
| `unit_price` | float | Цена на момент заказа       |

Создаётся и читается в составе заказа (агрегат Order). При создании уменьшается `parts.in_stock`.

### 6. Payment (платёж) — Order

| Поле           | Тип    | Описание                         |
| -------------- | ------ | -------------------------------- |
| `payment_uuid` | UUID   | Идентификатор платежа (PK)       |
| `order_uuid`   | UUID   | FK → orders                      |
| `amount`       | float  | Сумма                            |
| `method`       | string | CARD / SBP / CREDIT_CARD / …     |
| `status`       | string | PENDING / SUCCEEDED / FAILED     |
| `created_at`   | time   | Время создания                   |

| Операция | HTTP |
| -------- | ---- |
| Create   | при `POST .../pay` |
| Read (по заказу) | `GET /api/v1/orders/{order_uuid}/payments` |
| Read (один) | `GET /api/v1/payments/{payment_uuid}` |

**Способы оплаты:** `CARD`, `SBP`, `CREDIT_CARD`, `INVESTOR_MONEY` (также `UNKNOWN`).

## Соответствие методологии 12-Factor App

### I. Codebase

**Соответствует.**

Один репозиторий Git содержит весь исходный код приложения (Order Service, IAM Service, frontend, shared/platform, deploy). Одна кодовая база разворачивается в разных окружениях (локально / Docker Compose) одной и той же сборкой. Монорепозиторий с Go Workspaces не нарушает фактор: это одна база, а не несколько несвязанных приложений.

### II. Dependencies

**Соответствует.**

Зависимости Go явно объявлены в `go.mod` / `go.sum` модулей `order`, `iam`, `shared`, `platform`. Инструменты сборки и качества фиксируются через Taskfile (версии ogen, golangci-lint, goose и т.д.). Для OpenAPI-бандлинга используется `package-lock.json` (Redocly). Изоляция зависимостей обеспечивается модульной системой Go и контейнерной сборкой (multi-stage Dockerfile).

### III. Config

**Соответствует.**

Конфигурация читается из переменных окружения (`HTTP_*`, `POSTGRES_*`, `LOGGER_*`, `FRONTEND_DIR`, `IAM_HTTP_BASE_URL` и др.) в пакетах config. Секреты и параметры окружения не зашиты в код. Для локальной разработки `.env` подгружается через godotenv, но уже установленные переменные окружения имеют приоритет — это совместимо с 12-factor (config in the environment). Шаблоны: `deploy/env/.env.template`, генерация: `task env:generate`.

### IV. Backing services

**Соответствует.**

PostgreSQL (отдельные БД для Order и IAM) трактуется как подключаемый ресурс: адрес, порт, учётные данные задаются через env. IAM для Order — тоже backing service (`IAM_HTTP_BASE_URL`). Смена backing service сводится к смене конфигурации, без изменения кода. Файловое хранилище состояния приложения не используется.

### V. Build, release, run

**Соответствует (с оговоркой).**

- **Build:** multi-stage Dockerfile собирает бинарник Go и копирует миграции + frontend в образ.
- **Release:** образ + набор переменных окружения (`.env` / Compose) образуют релиз для запуска.
- **Run:** процесс HTTP-сервера в контейнере или локально (`task run`).

Оговорка: миграции также могут выполняться при старте приложения (удобство dev). Для соответствия фактору XII / чистоты стадий есть отдельная one-off команда `task migrate`.

### VI. Processes

**Соответствует.**

Order и IAM — stateless HTTP-процессы. Состояние хранится в PostgreSQL. Sticky-сессии и локальное дисковое состояние приложения не используются. Статический UI — файлы, раздаваемые процессом Order, без серверной сессии на диске.

### VII. Port binding

**Соответствует.**

Приложение само экспортирует HTTP-сервис через `ListenAndServe` на адрес из `HTTP_HOST`/`HTTP_PORT`. UI раздаётся тем же процессом Order. Compose пробрасывает порты наружу.

### VIII. Concurrency

**Соответствует.**

Горизонтальное масштабирование достигается запуском нескольких экземпляров сервисов за балансировщиком. Процессы stateless, общая БД — PostgreSQL. В локальном Compose для простоты одна реплика; модель процессов допускает scale-out без изменения кода.

### IX. Disposability

**Соответствует.**

Быстрый старт: лёгкий статический бинарник. Graceful shutdown по SIGINT/SIGTERM через `platform/pkg/closer`: остановка HTTP-сервера, закрытие пула БД, логгера и трейсера.

### X. Dev/prod parity

**Соответствует.**

Локально и в «стенде» используется один и тот же Docker-образ и PostgreSQL из Compose. Миграции goose одинаковы. Различия (host сервиса БД vs `localhost`, порты) вынесены в env. Интеграционные тесты используют Docker/Testcontainers.

### XI. Logs

**Соответствует.**

Логи пишутся как поток событий в **stdout** (Zap). Приложение не управляет ротацией и хранением логов — этим занимается окружение (Docker / коллектор).

### XII. Admin processes

**Соответствует.**

Административные задачи выполняются как one-off процессы в том же окружении:

- `task migrate` — применение goose-миграций к PostgreSQL;
- `task migrate:status` / `task migrate:down` — статус и откат.

Миграции используют тот же каталог SQL и те же параметры БД из `.env`, что и приложение.
