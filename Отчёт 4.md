# Отчёт 4. SLI, SLO и SLA

## Выбранные метрики

Три индикатора построены на метриках Order и IAM. Они отдаются в Open Metrics с отдельного порта `:9090` (`METRICS_HOST` / `METRICS_PORT`). VictoriaMetrics скрейпит поды по аннотациям `prometheus.io/*`. Синтетический пробер — blackbox-exporter (`deploy/k8s/blackbox.yaml`).

У Service `order` два порта: `8081` (UI/API) и `9090` (метрики). Команда `minikube service order -n spaceship --url` печатает **два URL**; для приложения нужен порт **30081**, второй URL — только `/metrics`.

| # | Метрика | Где пишется | Зачем как SLI |
|---|---------|-------------|----------------|
| 1 | `orders_created_total`, `orders_create_failed_total{reason}` | `order/internal/service/order/create.go` | Доля успешных созданий заказа (RBSLO) |
| 2 | `iam_logins_total{result="ok\|fail"}` | `iam/internal/service/auth/service.go` | Доля успешных логинов (RBSLO) |
| 3 | `http_requests_total{service,method,code}` | `platform/pkg/logger/http.go` → `platform/pkg/metrics` | Доступность HTTP: на стенде — RBSLO по запросам; в определении SLO — также TBSLO по минутам |

`orders_create_failed_total` — CounterVec: ряды с `reason` создаются при старте (в том числе нули), чтобы метрика сразу была в `/metrics` и vmui. Ряд `{reason="injected"}` растёт только после вызовов `CreateOrder` в режиме `DEMO_FAULT=create_fail`.

Дополнительно (не входят в три основных SLI): `http_request_duration_seconds`, `probe_success`, `orders_paid_total`, `orders_cancelled_total`, `orders_revenue_total`. Выручка — объём, не доступность.

**Окна.** Формулировка SLO — скользящие **7 дней**. На скринкасте в vmui — **Last 15 minutes** и `rate()[5m]` (иногда `[2m]`), иначе за пару минут график не успевает сдвинуться. Фиксированный диапазон дат в vmui (`relative_time=none`) для демо не используется: он не показывает «сейчас».

## SLI, SLO и SLA

### SLI-1. Успешность создания заказа (RBSLO)

```
SLI_create = rate(orders_created_total[W])
           / (rate(orders_created_total[W]) + rate(orders_create_failed_total[W]))
```

**SLO-1.** `SLI_create ≥ 99%` за 7 дней. Error budget: 1%.

На скринкасте: `W = 5m`. Пока `DEMO_FAULT=create_fail`, успешных create на новом поде нет → SLI_create → 0.

### SLI-2. Успешность логина (RBSLO)

```
SLI_login = rate(iam_logins_total{result="ok"}[W])
          / rate(iam_logins_total[W])
```

**SLO-2.** `SLI_login ≥ 99%` за 7 дней.

### SLI-3. Доступность HTTP

**Определение SLO (TBSLO).** Минута хорошая, если доля не-5xx за минуту ≥ 99%:

```
good_minute = (rate(http_requests_total{code!~"5.."}[1m])
            / rate(http_requests_total[1m])) >= bool 0.99

SLI_avail = avg_over_time(good_minute[W:1m])
```

**SLO-3.** `SLI_avail ≥ 99%` за 7 дней.

**На скринкасте** дополнительно показывается RBSLO по запросам за 5m — так быстрее видно 500 от `create_fail` (UI ещё даёт много 200 на whoami, поэтому TBSLO за 30m почти не падает):

```
sum(rate(http_requests_total{code!~"5.."}[5m]))
/ clamp_min(sum(rate(http_requests_total[5m])), 1e-9)
```

### SLA приложения

Пользователь Spaceship Orders в течение календарного месяца может регистрироваться, входить и оформлять заказы с доступностью **не ниже 99%**.

Общий SLA — логическое И по трём SLO. В MetricsQL сравнение без `bool` **удаляет ряд**, если условие ложно, и весь график становится пустым. Поэтому на графике:

```
SLA = (
  (SLI_create >= bool 0.99) +
  (SLI_login  >= bool 0.99) +
  (SLI_http   >= bool 0.99)
) / 3
```

`1` — все три цели выполнены; `0.66` / `0.33` / `0` — одно или несколько SLO красные.

Последствия на учебном стенде: фиксация инцидента, без денежных компенсаций.

`rate()` требует минимум двух scrape (интервал VictoriaMetrics **15s**). После `kubectl set env` под пересоздаётся, счётчики с нуля; смотреть SLI нужно **1–2 минуты на живом поде**, не выключая `create_fail` сразу.

## Изменения приложения для скринкаста

1. Отдельный HTTP-сервер метрик `:9090`; с публичного `:8081` путь `/metrics` снят.
2. Счётчики заказов и логинов; HTTP RED в middleware (без `/health`).
3. **`DEMO_FAULT`** читается при старте процесса:
   - `off` — обычная работа;
   - `create_fail` — **каждый** `CreateOrder` → 500 и `orders_create_failed_total{reason="injected"}`;
   - `login_fail` — все логины отклоняются;
   - `slow` — пауза 2s в `PayOrder` (на скринкасте можно не показывать).
4. `kubectl set env deploy/order DEMO_FAULT=…` пишет переменную в Deployment и **перезапускает под**. Это сильнее ConfigMap (`DEMO_FAULT: "off"`). Снять режим только так: `set env … DEMO_FAULT=off`, не повторным `apply` манифеста.
5. Blackbox-exporter и scrape `blackbox-health`; postgres-exporter у БД.

### Сценарий на видео

```bash
kubectl -n monitoring port-forward svc/vm-single-victoria-metrics-single-server 8428:8428
# vmui: http://localhost:8428/vmui  (не Victoria Logs :9428)
# диапазон: Last 15 minutes

minikube service order -n spaceship --url   # открыть URL с портом 30081 / 8081

kubectl -n spaceship set env deploy/order DEMO_FAULT=off
# UI: несколько успешных заказов
# vmui: orders_created_total ; SLI-1 ; vector(0.99)

kubectl -n spaceship set env deploy/order DEMO_FAULT=create_fail
kubectl -n spaceship rollout status deploy/order
# UI: спам созданиями 1–2 минуты (ошибка ожидаема)
# vmui Execute: orders_create_failed_total{reason="injected"}
# затем SLI-1 + vector(0.99) — линия ниже 99%
# затем HTTP 5m и SLA с >= bool 0.99

kubectl -n spaceship set env deploy/order DEMO_FAULT=off
# UI: снова 3–5 успешных заказов, иначе rate[5m] обнуляется
```

Запросы SLI/SLA — в поле Query vmui (не в shell). Второй query на графиках SLI: `vector(0.99)`.
